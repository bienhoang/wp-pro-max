## Source Anatomy

The source `wp-classic` is a **stack skill** meant to be always-active in a per-project `.claude/` configuration. It encodes conventions for a Classic PHP WordPress theme.

### Core components

1. **Stack declaration** — WordPress 6.x + Bedrock, PHP 8.2+, Classic PHP theme, optional Tailwind CSS 4 prefix, Standard ACF Pro.
2. **Project structure** — `templates/`, `parts/`, `inc/`, `assets/`, `acf-json/`, root templates (`front-page.php`, `page.php`, etc.).
3. **Naming conventions** — kebab-case template files, `snake_case` functions with theme prefix, `PascalCase` classes, `UPPER_SNAKE_CASE` constants.
4. **Code style** — WordPress Coding Standards (tabs), Prettier for JS/CSS.
5. **Template pattern** — `get_template_part('parts/name', 'variant', $args)` with `$args` defaults inside partials.
6. **Registration code** — `register_post_type()` / `register_taxonomy()` in `inc/post-types.php`.
7. **ACF pattern** — `acf_register_block_type()` in `inc/acf-blocks.php`; field groups authored in GUI and exported to `acf-json/`.
8. **Enqueue pattern** — `inc/enqueue.php` with `wp_enqueue_style/script`, `get_theme_file_uri()`.
9. **Anti-patterns / "What NOT to do"** — Blade, Acorn, `@include`, hardcoded colors, unsafe echo, inline scripts.

### Satellite artifacts

- `code-review` classic template — checklist tailored to a specific project name/prefix.
- `component-workflow` classic template — 11-step Figma-to-component process, spacing-token table, validation steps.
- `init.sh` — interactive installer that copies the stack skill and substitutes `{{VAR}}` placeholders.

## Challenge Questions

### 1. What is the correct integration surface — new skill, reference file, or both?

- **Source answer**: `wp-classic` is a top-level stack skill installed into the target project's `.claude/skills/stacks/`.
- **Local answer**: WP Pro Max is itself a plugin with top-level `skills/`. The `theme-conversion` skill already routes `classic-acf` to `references/classic-acf.md` (missing), and delegates authoring to `wp-theme-developer`.
- **Risk if wrong**: A standalone skill that no stage loads is dead code. A reference file alone is not user-discoverable.
- **Recommendation**: **Both** — create `skills/wp-classic/SKILL.md` (user-invocable) and `references/classic-acf.md` (consumed by `theme-conversion` and `wp-scaffold`). The skill can link to the reference, and the reference can instruct the agent.

### 2. How do we resolve the `templates/` vs root template file conflict?

- **Source answer**: Page templates live in `templates/` (`page-*.php`, `single-*.php`, `archive-*.php`).
- **Local answer**: `theme-conversion` maps roles to root files (`front-page.php`, `page.php`, `single-<cpt>.php`).
- **Risk if wrong**: Generated themes will have duplicate or misplaced templates; template hierarchy may not resolve correctly.
- **Recommendation**: **Keep root templates** for the WP Pro Max pipeline because they are the lowest-friction default for auto-generated themes. Mention `templates/` as an optional convention in the skill, but do not mandate it in the reference used by agents. Add a note that if a project already uses `templates/`, the agent should follow the existing structure.

### 3. Do we port the project-specific `code-review` and `component-workflow` templates?

- **Source answer**: They are generated per-project with substituted names/prefixes and live in `.claude/skills/project/`.
- **Local answer**: WP Pro Max does not generate per-project skills; it ships static kit skills.
- **Risk if wrong**: Clunky per-project generation adds complexity and conflicts with the manifest-driven pipeline.
- **Recommendation**: **Port as generic reference docs** inside `skills/wp-classic/references/` (e.g., `code-review-checklist.md`, `component-workflow.md`) without project-specific placeholders. Keep them reference-only, not user-invocable skills, until a project-specific skill mechanism exists.

### 4. How do we handle the GPL-3.0 → MIT license mismatch?

- **Source answer**: Source code is GPL-3.0; derivative works must be GPL-3.0.
- **Local answer**: WP Pro Max is MIT.
- **Risk if wrong**: Copying substantial text or code verbatim could force GPL-3.0 on the derived work or create license incompatibility.
- **Recommendation**: **Adapt, don't transplant.** Rewrite conventions in WP Pro Max's own words and structure. Use short, attributed excerpts only where necessary, and add a license/attribution note in the skill's reference section. Do not copy the source's `init.sh`, templates, or full prose.

### 5. What do we do with Figma/design-dir dependencies in the component workflow?

- **Source answer**: The classic component workflow depends on the `figma-bridge` skill and an optional `design/` folder.
- **Local answer**: WP Pro Max has no Figma or design-dir stage today.
- **Risk if wrong**: References to missing skills create broken workflow instructions.
- **Recommendation**: **Strip Figma-specific steps** from the ported component workflow. Keep the generic decomposition rules (check existing parts, map tokens to CSS variables, build + a11y check, update memory). If Figma support is added later, re-integrate.

### 6. Should the ported skill be user-invocable?

- **Source answer**: `user-invocable: false` (always-active stack skill).
- **Local answer**: WP Pro Max skills are typically user-invocable or auto-invoked by stage skills.
- **Risk if wrong**: A non-invocable skill may never be loaded; an always-loaded skill may add noise.
- **Recommendation**: **User-invocable: true** for `wp-pro-max:wp-classic` so users can ask "what are the classic theme conventions?" Stage skills will also load it by reference when strategy is `classic-acf`.
