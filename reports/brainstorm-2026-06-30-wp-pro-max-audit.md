# WP Pro Max Audit Command — Brainstorm Report

## 1. Problem statement & requirements

User asked two things:
1. What happens if you run `/wp-pro-max` with no subcommand?
2. Want a mechanism where running a command (old or new) scans the current project against a best-practice checklist and surfaces recommended fixes.

Agreed requirements for (2):

| # | Requirement | Detail |
|---|---|---|
| 1 | Form | New command `/wp-pro-max:audit` |
| 2 | Scope | Whole WordPress project, but only self-authored code (theme + plugin generated by WP Pro Max); skip core, vendor, third-party plugins/themes |
| 3 | Checklist | a11y (WCAG 2.2 AA), security, performance, code style / WordPress conventions |
| 4 | Output | Markdown + JSON report; write entry to `wp-build.json` (`audit` key) |
| 5 | Auto-fix | No auto-fix; read-only audit |
| 6 | Environment | Support both static mode (no wp-env) and live mode (wp-env running) |

Answer to (1): `/wp-pro-max` alone is **not defined**. Existing commands are all subcommands (`/wp-pro-max:<name>`). Running the bare prefix will result in “command not found”/no-op. To give it behavior we need to add `commands/wp-pro-max.md`.

## 2. Evaluated approaches

### A. Hybrid wrapper command (chosen)
`/wp-pro-max:audit` orchestrates existing skills (`wp-qa`, `wp-security`, `wp-a11y`, `wp-plugin-development`) plus a new lightweight code-style scan. It runs static checks when wp-env is absent, and live checks when wp-env is available.

Pros:
- Reuses 80% of existing logic and checklists.
- Consistent with manifest-driven, resumable pipeline.
- Easy to extend checklist by adding more skill references.

Cons:
- Slightly more orchestration code.
- Needs graceful degradation when wp-env not running.

### B. Standalone audit script
A single `scripts/audit.sh` with custom regex/static checks.

Pros:
- Fast, simple, no wp-env dependency.
- Easy to test in isolation.

Cons:
- Duplicates rules already in `wp-a11y`, `wp-security`, etc.
- Harder to keep in sync when checklist references evolve.

### C. Agent-driven deep audit
Each domain spawns a dedicated agent.

Pros:
- Deep, contextual analysis.
- Can reason about complex patterns.

Cons:
- Slow and token-heavy.
- Overkill for a repeatable checklist scan.

## 3. Final recommended solution

Implement `/wp-pro-max:audit` as a hybrid wrapper command:

1. **Command file**: `commands/audit.md` with frontmatter:
   - `description`: "Run a best-practice audit (a11y, security, performance, code style) on the current WP Pro Max project."
   - `argument-hint`: "[--scope self|all] [--live|--static] [--format md|json] [--out <path>]"
   - `allowed-tools`: [Read, Write, Edit, Bash, Glob, Grep, Task, Skill]

2. **Behavior**:
   - Locate `wp-build.json`; derive theme/plugin paths.
   - Detect wp-env status (`wp-env run cli wp option get home` or `.wp-env.json` + container check).
   - **Static phase** (always runs):
     - Code style: run `phpcs` with WPCS if available; fallback regex checks (sanitization, escape, nonces, caps).
     - a11y: run axe on source/optimized HTML or theme templates.
     - Security: run `secrets-scan.sh` on theme/plugin; check file permissions guidance.
   - **Live phase** (only if wp-env running):
     - Performance: `wp-qa` CWV + `wp-performance-backend` TTFB/query count/autoload.
     - Security: `wp-security` vuln scan of active plugins/themes.
     - a11y: browse local URLs with axe.
   - Aggregate findings by severity (`critical|high|medium|low|info`) and category.
   - Write `audit` entry to `wp-build.json` with `summary`, `findings[]`, `passed`, `generatedAt`, `mode`.
   - Write human report to `docs/audit-<timestamp>.md` and machine report to `audit-<timestamp>.json`.

3. **Scope defaults**:
   - `--scope self` (default): theme path from `theme.path` + plugin path if `wp-plugin.json` exists.
   - `--scope all`: include third-party plugins/themes but mark them as read-only/external.

4. **Checklist mapping**:

| Category | Static checks | Live checks (wp-env) |
|---|---|---|
| a11y | axe on HTML/templates, wp-a11y rules, landmarks/headings/alt/contrast | axe on rendered URLs |
| security | secrets scan, regex for `$_GET/$_POST` without sanitize, missing nonces/cap checks, SQL direct | wp-security hardening/vuln scan, active user audit |
| performance | asset size/count, inline scripts, image sizing | CWV, TTFB, query count, autoload, cron |
| code style | PHPCS/WPCS, namespace/text-domain checks, hook naming | n/a |

5. **Root command behavior** (optional but recommended):
   - Add `commands/wp-pro-max.md` that prints available commands, current project status, and suggests next step.

## 4. Implementation considerations & risks

- **Idempotency**: Audit is read-only but still writes to `wp-build.json`. Use `wpbuild_set` safely.
- **wp-env detection**: Must not fail if Docker is missing; degrade to static mode with a note.
- **PHPCS availability**: If `vendor/bin/phpcs` or WPCS not installed, document fallback regex rules clearly.
- **Scope exclusion**: Need robust ignore patterns (`node_modules`, `vendor`, `.wp-env`, `wp-content/plugins/*` unless self-mapped).
- **Theme strategy differences**: Classic/Block/Page-builder output different file types; scan rules must adapt (PHP vs HTML vs theme.json).
- **Report size**: Cap findings per category to avoid huge output.

## 5. Success metrics & validation criteria

- `/wp-pro-max:audit` runs to completion in both static and live modes.
- Report contains at least one finding per requested category when issues exist.
- `wp-build.json` contains `audit.summary.passed` boolean and `audit.findings[]`.
- No auto-fixes applied; existing files unchanged except report/manifest.
- Re-running produces stable output (idempotent).

## 6. Next steps & dependencies

1. Create `commands/audit.md`.
2. Create `skills/wp-audit/SKILL.md` (or keep logic inside command if simple).
3. Add helper script `scripts/audit-aggregate.sh` to normalize output from multiple scanners.
4. Update `schemas/wp-build.schema.json` with `audit` property.
5. Optionally create `commands/wp-pro-max.md` for root command help.
6. Validate plugin with `claude plugin validate .`.
